# 데이터베이스 복구 기준

5ft magazine의 DB는 초기 수동 스키마와 이후 Supabase 마이그레이션으로 구성된다.
새 프로젝트 또는 재해 복구 환경에서는 아래 순서를 사용한다.
**스키마 재현은 데이터 백업 복구가 아니다.** 이 문서와 로컬 검사만으로 운영 백업,
Auth 로그인, Storage 파일 복구가 검증됐다고 기록하지 않는다.

## 기준 파일

1. `db/baseline-manifest.json`이 초기 스키마의 유일한 적용 순서를 정의한다.
2. `npm run db:baseline`이 원본 SQL을 `db/baseline.sql`로 합친다.
3. `db/baseline.sql` 적용 후 `supabase/migrations/*.sql`을 파일명 순서로 적용한다.
4. `npm run db:audit`으로 클라이언트가 사용하는 테이블·뷰·RPC가 모두 추적되는지 확인한다.

`db/baseline.sql`은 생성 파일이다. 직접 수정하지 않고 개별 `db/*-schema.sql`을 수정한다.

## 격리 환경의 스키마 재현

아래 적용 명령은 쓰기 작업이다. 운영 프로젝트에 실행하지 않는다. 승인된 별도
복구 프로젝트를 만들고 프로젝트 ref와 연결 대상을 두 사람이 대조한 뒤 실행한다.
복구용 작업 디렉터리를 따로 써서 기존 운영 CLI 연결을 바꾸지 않는다.

```bash
npm ci
npm run db:baseline:check
npm run db:audit
```

그다음 **격리된** 새 Supabase 프로젝트의 SQL Editor에서 `db/baseline.sql`을 적용하고,
Supabase CLI로 마이그레이션을 적용한다.

```bash
supabase link --project-ref <새 프로젝트 ref>
supabase db push --include-all
```

이 경로는 빈 프로젝트의 스키마 재현용이다. 전체 DB 백업을 복원하는 훈련에서는
백업에 포함된 스키마·마이그레이션 이력을 먼저 대조하고, baseline을 무조건 다시
적용하지 않는다. 백업 시점 이후의 필요한 마이그레이션만 적용한다.

`20261003000003_log_retention_schedule.sql`은 pg_cron이 있으면 일일 로그 정리를
예약한다. 복구 데이터 대조가 끝나기 전에는 격리 환경의 해당 작업을 비활성화한다.
로컬 확장이 없으면 경고와 함께 예약을 생략하므로 마이그레이션 성공만으로 예약
성공을 판단하지 않는다. [운영 검증 절차](operations-verification.md)를 따른다.

## 백업 범위 확인

먼저 담당자가 Dashboard에서 실제 요금제, 백업 종류(논리/물리), 최신 성공 시각,
가장 오래된 복원 가능 시각, 보관 기간, PITR 활성 여부와 복원 범위를 기록한다.
이번 작업에서는 현재 운영 백업의 존재·주기·복원 가능 여부를 직접 확인하지 않았다.

DB 백업의 범위는 사용한 방법에 따라 다르다. Auth 스키마·역할이 포함됐는지
백업 manifest와 해당 방법의 설명으로 확인한다. Supabase DB 백업에는 Storage
객체의 메타데이터만 있고 실제 파일은 포함되지 않는다.
([Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups))

SQL baseline에는 Auth 사용자 데이터나 Storage 이미지·PDF의 실제 내용이 없다.
파일은 별도 암호화 백업과 객체 manifest(버킷·키·크기·체크섬·백업 시각)가 필요하다.
백업 파일, 사용자의 이메일·전화번호, 주문·메시지 본문, 키, 토큰은 저장소나 검증
기록에 넣지 않는다. 기록에는 권한 제한된 증거 위치와 집계 결과만 남긴다.

## 복구 훈련

정기 훈련은 분기 1회와 주요 DB/Auth/Storage 변경 후를 제안한다. 이는 아직
수행된 일정이 아니다. 담당자·승인자·백업 접근 권한·훈련 날짜부터 지정한다.
실제 restore, 사용자 생성, 파일 복사, cron 변경은 자동 health 검사에 포함되지 않는다.

1. **격리와 승인:** 새 테스트 프로젝트와 전용 테스트 계정을 사용한다. 실사용자
   메일·푸시, webhook, 결제·커머스 쓰기 호출, 운영 버킷 쓰기를 차단한다. 민감한
   백업을 다루는 대상은 비공개로 두며 데이터 반입·파기 정책을 사전에 승인받는다.
2. **DB 테스트:** 승인된 백업을 격리 프로젝트에 복원한다. 백업 시점의 스키마,
   마이그레이션 이력, 업무 테이블 집계 수, 참조 무결성, RLS·뷰·RPC 권한을 확인한다.
   anon·본인·다른 사용자·편집부 역할을 각각 시험한다. 빈 스키마 생성 통과나
   `db:audit` 통과만으로 구매 내역·메시지·사진 레코드가 복원됐다고 판단하지 않는다.
3. **Auth 테스트:** 백업에 실제 사용자·identity 데이터가 포함되는지 먼저 확인한다.
   복원 또는 이전 방법에 맞춰 UUID와 profiles/주문 권한의 연결을 대조하고, 승인된
   테스트 계정으로 로그인·로그아웃·토큰 갱신·다른 사용자 접근 거부를 시험한다.
   OAuth 공급자, redirect URL, SMTP, JWT 관련 설정과 시크릿은 별도 구성·점검한다.
   Auth 행 수만 같아도 로그인 검증을 통과한 것은 아니다.
4. **Storage 테스트:** 별도 객체 백업을 테스트 버킷에 복사하고 manifest의 객체 수,
   총 용량, 체크섬을 대조한다. DB 메타데이터와 누락·고아 객체를 확인한다. 테스트
   사진 표시와 PDF 실제 바이트 다운로드·열람을 확인하고 버킷 공개 여부, 열거,
   업로드·삭제 권한을 별도로 시험한다. 메타데이터 행만 복원되면 실패로 기록한다.
5. **통합 테스트:** 격리 사이트에서 공개 화면, 테스트 계정 로그인, 합성 사진 응모,
   장터, 테스트 Magazine 열람을 확인한다. Shop·결제는 sandbox 또는 읽기만 허용한다.
   운영 health 검사와 첫 cron 성공 이력을 확인한 뒤 각 영역의 결과를 따로 판정한다.
6. **종료:** 시작·백업 복원·각 검증 완료 시각, 실패 항목, 재시험 담당자를 기록한다.
   승인된 파기 절차로 테스트 데이터와 임시 시크릿을 정리한다. 운영 전환이나 실제
   장애 복구는 별도 승인 대상이며 이 훈련 문서가 실행 허가는 아니다.

## 복구 목표 제안

RPO는 허용 가능한 데이터 손실 시간, RTO는 서비스 검증까지 허용할 복구 시간이다.
아래는 **승인이 필요한 초기 목표이며 현재 달성 사실이나 보장 SLA가 아니다.**

| 영역 | 제안 RPO | 제안 RTO | 달성 전제와 확인 |
|---|---|---|---|
| DB 업무 데이터 | 24시간 | 4시간 | 일일 성공 백업·접근 권한 확보, 실제 데이터와 RLS 복구 훈련 |
| Auth | 24시간 | 4시간 | 사용자·identity 백업 범위와 공급자 설정 확인, 실제 테스트 로그인 |
| Storage 실제 파일 | 24시간 | 8시간 | 별도 일일 객체 백업, 전체 manifest와 다운로드·체크섬 확인 |

주문 등 24시간 손실을 허용할 수 없는 업무는 운영자가 별도로 목표를 승인하고 PITR
또는 대체 보존 방법의 비용·지원 범위를 확인해야 한다. PITR 미활성 상태를 활성으로
가정하지 않는다. 통합 RTO는 DB 완료 시각이 아니라 Auth·파일·화면 검증을 모두
마친 시각으로 측정한다. 실제 RPO는 장애 기준 시각과 확인된 마지막 복구 데이터
시각의 차이, 실제 RTO는 훈련 시작과 검증 완료 시각의 차이로 기록한다.

## 변경 규칙

- 초기 수동 객체를 수정하면 원본 스키마와 baseline을 함께 갱신한다.
- 신규 변경은 항상 `supabase/migrations`에 재실행 안전한 SQL로 추가한다.
- CI는 baseline 동기화와 신규 DB drift를 실패로 처리한다.
- 프로덕션 데이터가 있는 컬럼에 제약을 추가하기 전 실제 위반 데이터를 확인한다.
